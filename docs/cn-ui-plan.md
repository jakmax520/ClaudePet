# 界面中文化 —— 方案评估

> 状态：**评估完成，尚未实施**。本文给出结论、设计与工作量，供后续实施时参照。
> 评估日期 2026-10-15。

## 结论先行

**可行，推荐「自制点阵字模」方案。** 规模：181 个不同汉字 + 95 个 ASCII 字符，
字模约 **7.5KB**，存 flash 不占堆。改动集中在新增两个文件 + 替换 `main.cpp` 的
约 93 处文案。

**并支持运行时中英切换**（设置里加一项）。这不额外增加字模体积 —— 英文文案
本来就必须走同一套点阵（见 §3.6），双语与纯中文的成本几乎相同。

有一条**无法消除的限制**：主机通过蓝牙下发的动态文字（状态消息、工具名、
参数提示）设备不知道语义，**翻不了** —— 无论选哪种语言都按英文原样显示。

---

## 一、硬约束

这三条决定了可选方案的范围。

### 1. TFT_eSPI 的内置字体不含汉字

本项目的文字全部走 TFT_eSPI 的 GLCD 位图字体（`setTextSize(1)` = 6×8），
字符集只有 ASCII。汉字无法用它绘制。

### 2. 现成中文字体文件装不下

TFT_eSPI 显示矢量中文的唯一官方途径是 **Smooth Font**：把 `.vlw` 字体文件放进
文件系统，用 `loadFont()` 加载。但 `loadFont()` 会把**整个字体文件读进堆**。

本板无 PSRAM，满屏 16 位精灵图（153.6KB）之后**堆只剩约 32KB**（实测
`free=31892 / largest=13300`）。而含 CJK 的 `.vlw` 即便裁剪到本节用到的 200 字
以内，也远超这个数。**故 Smooth Font 路线直接排除。**

### 3. 主机下发的文字无法翻译

这些字符串由 Claude Desktop / 主机经 BLE 下发，设备只负责显示，无从知道语义：

| 界面位置 | 来源字段 | 实际内容 |
| --- | --- | --- |
| HUD 状态行 | `tama.msg` | `buddy_check busy` 之类 |
| HUD 转写行 | `tama.lines[]` | 主机的活动描述 |
| 审批页 | `tama.promptTool` | 工具名，如 `Bash` |
| 审批页 | `tama.promptHint` | 参数提示，如 `/tmp/x` |
| 顶部标题 | `ownerName()` | 用户在主机上设的名字 |

**最终界面形态是「本地固定文案中文 + 主机动态内容英文」的混排**，这不是实现
取舍，是协议决定的。除非将来主机侧下发中文。

---

## 二、方案对比

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| A. Smooth Font | `.vlw` 字体放 LittleFS，`loadFont()` 加载 | **排除** —— 字体数据整块进堆，32KB 装不下 |
| B. **自制点阵字模** | 只取用到的字，1bpp 点阵存 PROGMEM，自己写绘制函数 | **推荐** —— 7.5KB，零堆占用 |
| C. 图标化 / 拼音化 | 不显示汉字，用图标或拼音替代 | 不满足需求 |

方案 B 之所以成立，关键在于只嵌入**实际用到的那 181 个字**，而不是整套字库。

## 三、方案 B 的设计

### 3.1 新增文件

| 文件 | 内容 | 生成方式 |
| --- | --- | --- |
| `tools/gen_cn_font.py` | 字模生成工具 | 手写 |
| `src/font_cn.h` | 字模数据 + 索引表 | **由工具生成，不手改** |
| `src/cn_text.h` / `.cpp` | 渲染层 | 手写 |

### 3.2 字模数据布局

- **汉字**：16×16，1bpp，每行 2 字节 → **32 字节/字**
- **ASCII**：16×8 半宽，1bpp → **16 字节/字符**
- **索引**：按码点排序的 `(uint32_t codepoint, uint16_t offset)` 表，二分查找；
  或对 181 个汉字用简单的线性/哈希查找（数据量小，线性也够快）

体积：`181×32 + 95×16 + 索引 362 ≈ 7.5KB`

> 字模源字体选**黑体（`simhei.ttf`）**：小尺寸点阵下无衬线字形比宋体清晰，
> 笔画不会糊成一片。工具里会先渲染再按阈值二值化，阈值需要实机调。

### 3.3 渲染层接口

```cpp
// 画一行 UTF-8 文本。背景色一并填充 —— 精灵图上必须覆盖旧内容，否则残影。
void cnDraw(TFT_eSPI* t, int x, int y, const char* utf8,
            uint16_t fg, uint16_t bg);

// 以 x 为中心绘制（替代 TFT_eSPI 的 MC_DATUM 语义）
void cnDrawCenter(TFT_eSPI* t, int cx, int y, const char* utf8, ...);

// 测量像素宽度 —— 居中和换行都要用
int  cnWidth(const char* utf8);

// 带格式化的版本，支持数字混排：cnPrint(t, x, y, "电池 %d%%", pct)
void cnPrint(TFT_eSPI* t, int x, int y, uint16_t fg, uint16_t bg,
             const char* fmt, ...);
```

**实现要点**：

- 逐像素 `drawPixel` 画 16×16 = 256 次，对每帧要重绘的多行文字略显浪费。
  优化路径：把单字先展开成 16×16 的 16 位色小数组（512B，栈上），再用
  `pushImage` 一次贴上去。**先按简单的逐像素实现，实测帧率不够再优化。**
- 文本要 `CN_DRAW_BG` 双色绘制。精灵图上的文字若只画前景，先前内容会残留。

### 3.4 布局影响（**这是最容易被低估的部分**）

字号从 6×8 变成汉字 16×16 / ASCII 16×8，**所有排版常量都要重算**：

| 位置 | 当前 | 中文方案 | 影响 |
| --- | --- | --- | --- |
| 浮层菜单 | 宽 150px，size 1 | 汉字 16px | 4 字 = 64px，够用；行高需从 16 加大 |
| 设置面板 | 同上 | 同上 | 「屏幕方向」4 字 = 64px，值「竖屏」32px |
| 信息页 | 每行 8px 高，最多 40 列 | 行高需 ≥16px | **行数减半**，内容要重新分组 |
| HUD | 40 列 × 6px = 240px | 40 列 × 8px = 320px **溢出** | `MSG_COLS` 需 40 → 30 |
| 审批页 | `%.21s` 截断 | 21 字符 × 8px = 168px | 可放宽到 30 字符 |

> **HUD 是主要风险点**：它显示的是主机下发的英文长文本，`wrapInto()` 按
> 字符数换行。ASCII 从 6px 变 8px 后，若不把 `MSG_COLS` 从 40 降到 30，
> 文字会超出屏幕右边缘。

### 3.5 字模生成工具

```bash
python tools/gen_cn_font.py          # 读取文案表，重新生成 src/font_cn.h
```

工具内维护一份**文案表**（`texts` 列表）。改文案后重跑即可，汉字集合自动更新。
这解决了「漏字」问题 —— 少打一个字会在生成时暴露，而不是等到设备上显示成空白。

### 3.6 中英切换

设置里加一项 `language` / `语言`（`Settings` 结构加 `uint8_t lang`，随 NVS 持久化）。

**为什么不额外增加成本**：本项目要混排，而主机下发的英文内容**必须能显示**，
所以 ASCII 点阵字模无论如何都得有（1.5KB）。既然 ASCII 已在字库里，英文文案
改走同一条渲染路径是顺带的事。

文案组织从「硬编码字符串」改为**双语查表**：

```cpp
// 每条文案两个版本。切换语言只是改这个下标。
enum { L_EN = 0, L_ZH = 1 };

static const char* const MENU_ITEMS[][2] = {
  { "settings", "设置" },  { "turn off", "关机" },
  { "help",     "帮助" },  { "about",    "关于" },
  { "demo",     "演示" },  { "close",    "关闭" },
};
// 绘制处：
cnDraw(&spr, x, y, MENU_ITEMS[i][settings().lang], p.text, PANEL);
```

**布局要按两种语言中较宽的那个排。** 多数条目差别不大（`clock rot` 9 字符
= 72px vs `屏幕方向` 4 字 = 64px），但个别差得多：

| 条目 | 英文 | 中文 |
| --- | --- | --- |
| brightness | 10 字符 = 80px | 2 字 = 32px |
| factory reset | 13 字符 = 104px | 4 字 = 64px |
| delete char | 11 字符 = 88px | 4 字 = 64px |

英文更长，所以**按英文排版即可同时容纳中文**。反过来则不行 —— 这也是为什么
面板宽度不能按中文压缩。

**ASCII 字模需覆盖主机可能下发的字符**：95 个可打印 ASCII（0x20–0x7E）能覆盖
绝大多数情况。若主机发来点阵里没有的字符（如全角标点、emoji），会渲染成空白
—— 生成工具里应对此**显式告警**，而不是静默跳过。

## 四、工作量

| 项目 | 估计 |
| --- | --- |
| 字模生成工具 | 中（Pillow 渲染 + 二值化 + 导出 C 数组） |
| 渲染层 | 中（约 150 行 C++） |
| 文案替换 | **大** —— `main.cpp` 约 93 处 |
| 布局重排 | **大** —— 菜单 / 信息页 / HUD / 审批页都要重算 |
| 双语查表改造 | 小 —— 文案集中成二维表，切换只是改一个下标 |
| 语言设置项 | 小 —— 复用现有设置机制（`Settings` 加字段 + NVS 键），设置项数 10 → 11 |
| 实机调试 | 中（点阵清晰度、阈值、行距需要目视调） |

**双语相对纯中文的增量成本很小**，因为两者共用同一套渲染路径与字库，只多一张
二维表和设置里的一项。

**主要成本不在字体本身，在排版重排。** 汉字比原字形大一倍，所有按像素硬编码
的坐标都要复核。

## 五、风险

1. **点阵可读性**：16×16 对「繁」「警」这类笔画密集的字可能糊。实机确认，
   必要时部分字改 12×12 加粗 或调二值化阈值。
2. **HUD 换行**：见 3.4，需要同步调整 `MSG_COLS` 与 `wrapInto()` 的宽度参数。
3. **帧率**：文字逐像素绘制在主循环里，需实测；不够则改 `pushImage`。
4. **观感落差**：点阵不如矢量精致，且中文（16×16）与数字（16×8）风格需协调。
5. **字体授权**：`simhei.ttf` 随 Windows 分发，**再分发字模数据前需确认授权**。
   若在意，可换思源黑体 / 文泉驿（SIL OFL / GPL）等自由字体重生成。

---

## 六、顺带该修的既有问题

翻译时会改到这些字符串，其中几处**内容本身就是错的**（上游两键布局的遗留），
一并修正比单纯直译更好：

| 位置 | 现状 | 问题 |
| --- | --- | --- |
| 关于页 | `Press A on a prompt to approve from here.` | 本板审批键是 **OK**，不是 A |
| 致谢页 | `hardware: M5StickC Plus / ESP32 + AXP192` | 本板是 **FoloToy AI Passport / ESP32-C3** |
| 宠物页 | `face-down to nap` | 本板**无 IMU**，翻面打盹失效 |
| 关于页 | `18 species.` | 实际是 18 种 ASCII + 1 个 GIF 角色包 |

## 七、待决策

实施前需要确认：

1. **字体的授权取向** —— 用系统黑体（`simhei.ttf`，随 Windows 分发，**再分发
   字模前需确认授权**），还是换思源黑体 / 文泉驿等自由字体重生成。
2. **中文字号** —— 16×16（清晰，但排版改动大）还是 12×12（紧凑，HUD 几乎不用改，
   但笔画密的字会糊）。
3. **专有名词** —— `Claude`、`BLE`、`USB`、`Lv` 这类保留英文还是也译（「等级」）。
4. **默认语言** —— 固件出厂默认中文还是英文。
